## Abstract

This CIP proposes consolidating the data frame implementations between lynguine and referia to reduce duplication, improve maintainability, and clarify the boundaries between core and review-specific functionality.

## Motivation

The current implementation shows potential duplication between lynguine and referia's CustomDataFrame classes. This leads to:
- Maintenance overhead
- Potential inconsistencies
- Unclear boundaries between core and review-specific functionality
- Risk of divergence between implementations

## Specification

### 1. Data Storage Standardization
- Align referia's data storage with lynguine's structure
- Remove the `_data` property override unless there's a compelling reason for the difference
- Document the data storage model clearly

### 2. Property Accessor Consolidation
- Move common property accessors to the base class
- Keep only review-specific properties in referia's implementation
- Document the property hierarchy

### 3. Method Override Review
- Audit all method overrides in referia's implementation
- Document which overrides are necessary for review functionality
- Consider moving common functionality to lynguine

### 4. Compute Integration
- Resolve the placement of compute functionality
- Document the decision and rationale
- Ensure clear separation of concerns

### 5. Data Augmentation
- Review augmentation methods in both implementations
- Identify common patterns that could be moved to lynguine
- Keep only review-specific augmentation in referia

## Backward Compatibility

The following changes have backward compatibility implications:

1. **Data Storage Changes**
   - Changing the data storage structure could break existing code that relies on the current `_data` property
   - Need to maintain both access patterns during transition
   - Consider deprecation period for old access pattern

2. **Property Accessor Changes**
   - Moving properties to base class could affect inheritance behavior
   - Need to ensure existing property overrides continue to work
   - May require adapter pattern during transition

3. **Method Override Changes**
   - Moving methods to base class could change behavior of existing overrides
   - Need to carefully review all override points
   - Consider maintaining both implementations during transition

4. **Compute Integration**
   - Moving compute functionality could affect existing compute workflows
   - Need to ensure compute hooks continue to work
   - May require adapter layer during transition

## Implementation Plan

1. Create a detailed audit of duplicated functionality
2. Document the current inheritance structure
3. Propose specific changes for each area
4. Create migration plan for any changes
5. Update documentation to reflect the new structure

## Questions to Resolve

1. Why does referia use a different data storage structure?
2. Which method overrides are truly necessary for review functionality?
3. Should compute functionality be moved to lynguine?
4. What augmentation functionality should be core vs review-specific?
