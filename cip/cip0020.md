# CIP-0020: Windowed `inline_list` GET with page size and on-demand append

> **Note**: CIPs describe HOW to achieve requirements (WHAT).
> Use `related_requirements` to link to the requirements this CIP implements.

## Status

- [x] Proposed - Initial idea documented

- [ ] Implemented - Work complete, awaiting verification
- [ ] Closed - Verified and complete

## Summary

`display.layout: inline_list` keeps its CIP-0010 meaning — list chrome, filter/sort instead of the record selector, mark in place — but the first HTML response paints **at most N working rows**. Further rows append as a fragment (infinite scroll via HTMX `revealed`, with a Load more control as fallback). Populate-all is unchanged: it still loops `working_indices()`, not the painted page.

This is the listing-GET counterpart of CIP-001D. 001D is the long POST. This CIP is the GET that currently does `set_index` + `_current_data` for every working index before the browser sees a byte.

Addresses [REQ-0017](../requirements/req0017_bounded-inline-list-get.md), [REQ-000E](../requirements/req000E_named-layout-compositions.md) (`inline_list` stays the named list composition), and [REQ-0009](../requirements/req0009_multi-config-web-hosting.md) (one listing GET must not freeze the root server’s only worker).

## Motivation

On 2026-10-29, `07_grounds` was switched to `inline_list` so Classify all would exist. The page never came back. The worker sat at 100% CPU; `curl --max-time 25` received 0 bytes. The same walk is why `02_embed` over 2013 units is painful on GET.

`_panel_response_context` does:

```python
for idx in working:
    reviewer.set_index(idx)
    data = _current_data(reviewer)  # get_row_data + get_value per widget
```

Timed locally under CIP-001D: ~6 s for 50 fat extract rows, ~4 minutes estimated for 2013, before HTML size. Catalogs still open because they are thin (identity + `complete`) and CIP-001C windows `/today/` on `today±30d`. That is not a listing contract. It is luck about widget cost and filters.

CIP-0010 forbade **one-row-only paging** (285 configs must not become 285 `side_by_side` pages). CIP-001D listed “pagination of `inline_list` catalogs” as a non-goal on the assumption catalogs stay short. Both still hold: this CIP windows the **same list**, it does not revert to the record selector.

The 07 workaround (`side_by_side` + `args.all: true` chrome) is valid unit review. It is not an answer for authors who want a vertical list of many entries.

## Detailed Description

### What stays

| Piece | Owner |
|-------|--------|
| List chrome, filter/sort instead of selector | CIP-0010 / REQ-000E |
| Filter/sort over the **full** working set | CIP-0010 |
| Populate-all loop and cache flush | CIP-001D |
| Catalog schedule filters | CIP-001C |
| No third named layout | REQ-000E |

### Window

`display.list_page_size` is an integer. Default **50** when omitted (the CIP-001D 50-row timing is already interactive). **0** restores today’s unbounded walk for a short catalog that must paint in one response.

The window is a slice of `working_indices()` **after** filter and sort:

```text
page = working[offset : offset + page_size]
```

`offset` is a query/form field (`list_offset`), default 0. Filter/sort POSTs reset offset to 0.

The nav counter still shows the **working-set** size (“2013 items”), not the page size. Select-all / Classify all / Extract all counts use `len(working)`, never `len(page)`.

### First GET vs append

Two responses share the listing renderer:

1. **Panel** (`list_offset=0`, ordinary GET or filter POST). Renders intro, listing chrome (parameters, Classify all), the first page of rows, then a sentinel.
2. **Fragment** (`list_offset>0` and HTMX request). Renders only the next page’s `<li>` / group sections plus a replacement sentinel. Does **not** call `_panel_response_context` for the full panel. Does **not** re-run listing chrome.

Sentinel (web):

- `hx-get` the same review URL with `list_offset` advanced by `page_size`
- `hx-trigger="revealed"` (infinite scroll)
- `hx-swap="outerHTML"` on the sentinel itself after appending rows to the listing `<ul>` (or `beforeend` on a stable `#inline-listing-rows` target)
- Visible **Load more** control with the same URL for browsers/AT that do not fire `revealed`

When `offset + page_size >= len(working)`, omit the sentinel.

### Cost still inside the page

Fifty fat rows still call `_current_data` fifty times. That is acceptable (~6 s). A later phase may snapshot listing columns without per-widget `get_value` / `named_store_status` `refresh: true`. Out of scope for v1 if the window is in place; do not block the window on a new data API.

### Jupyter

Same `list_page_size`. No HTMX: a Load more control (or ipywidgets equivalent) appends the next slice. Filter still resets the window.

### Config example

```yaml
display:
  layout: inline_list
  list_page_size: 50   # omit for the default; 0 = unbounded
```

`02_embed` / `07_grounds` can return to `inline_list` once this ships. They do not have to; `side_by_side` plus `args.all` remains the unit-review composition.

### Alternatives rejected

| Alternative | Why not |
|-------------|---------|
| New layout name (`paged_list`) | REQ-000E’s set stays small. This is the list composition with a window, not a new document class. |
| Filter-only bound | `/year/` and unit workbenches have no date window that makes 2013 rows small. |
| Always `side_by_side` for N>k | Loses mark-in-place. CIP-0010’s point. |
| Virtual DOM / client-side row store | Referia rows are server widgets. Append HTML fragments. |
| SSE listing | Does not persist offset; still one huge first walk unless windowed. |

### Non-goals

- Changing populate-all’s HTTP lifetime or cache flush (CIP-001D).
- A job queue.
- Cheap listing snapshots (phase 2).
- Changing CIP-0010’s tall-first catalog model.

## Implementation Plan

1. **Slice helper** (not HTML in `routes.py`):
   - `list_page_size` from display config (default 50, `0` unbounded).
   - `working_window(reviewer, offset) -> (page_indices, remaining)`.
2. **Panel path**:
   - `inline_list` GET/filter walks **only** `page_indices`.
   - Populate-all chrome count stays `len(working_indices())`.
   - Emit sentinel / Load more when `remaining > 0`.
3. **Fragment path**:
   - Same review URL or a dedicated `/listing-page` that reuses `render_inline_listing`’s row loop.
   - Returns rows + sentinel only.
4. **Jupyter**: Load more appends the next slice; no `revealed`.
5. **Docs**: CIP-0010 testing line “not one-row-only paging” stays; add “windowed list is still a list.” CIP-001D non-goal “pagination of catalogs” points here.

## Backward Compatibility

Default 50 changes `/` and `/year/` if those catalogs exceed 50 matching rows: the rest appear on scroll. That is the intended catalog behaviour once the year list is large. `list_page_size: 0` restores one-shot paint.

Fragment requests must not drop filter/sort query state.

## Testing Strategy

- 20-row catalog GET: one page, no sentinel (N ≤ page size).
- 2013-row fixture: first GET renders 50 rows and a sentinel; fragment at `list_offset=50` renders the next 50 and does not include listing chrome.
- Filter POST resets to offset 0 and still reports the full working count.
- Extract all / Classify all `hx-post` still uses `/populate-all/{field}` with working-set count, not 50.
- `list_page_size: 0` walks every working index (short-catalog escape).
- Timed GET of the 2013-row fixture stays on the order of the 50-row measurement, not minutes.
