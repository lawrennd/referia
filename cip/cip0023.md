## Summary

Present the formats study (and later any permalink-tree study) as a
**directed graph of stages**: nodes are referia pages, edges are store
dependencies (who reads whose output). Expanding a node shows that
stage’s `parameters.yml` knobs. The analyst ticks checkboxes on
individual parameters and/or on whole stages to mark what enters the
**analysis-choice product** (multiverse).

Phase 1 is the view + a durable selection store that drives the
existing cheap product on main-run 07 codes
(`run_analysis_multiverse` from CIP-001E). Phase 2 widens which ticks
are executable (estimator knobs on `07_part_b`, then declared refits
such as `03_vq` → `04_grain` → `06_compare`). Open-ended “tick any
LLM stage and re-run the world” stays out of scope until cost classes
and product bounds are explicit.

Addresses the robustness / analysis-choice outcome under
[REQ-0015](../requirements/req0015_formats-part-a-b-in-referia.md)
and the dialogue pipeline surface of
[REQ-0010](../requirements/req0010_dialogue-pipeline-in-referia.md).
Builds on CIP-001E’s `11_multiverse` page, CIP-0011 Plotly viewers,
and CIP-0016 document-level compare compute.

## Motivation

`11_multiverse` today is a PopulateButton over a fixed cartesian
product (definition × weighting × exclusion × threshold × round) with
almost no study-facing explanation of *which* upstream choices that
product is allowed to vary. The paper’s multiverse is a product over
**named analytical choices**, not a silent re-run of every
`parameters.yml` key.

Analysts (Jess in particular) need to see:

1. What is connected to what in the reconstruction as done
2. Which knobs sit on each connection / stage
3. A clear place to say “vary this” vs “hold this fixed”

Without that view, expanding the multiverse either stays opaque
(hard-coded axes in compute) or becomes unbounded (every parameter ×
every LLM stage).

## Detailed Description

### What the user sees

On `11_multiverse` (permalink `/11_multiverse/`), a **pipeline DAG**
viewer:

| Element | Meaning |
|---------|---------|
| Node | One referia stage page (`01_chunk`, `02_extract`, …, `07_part_b`, sidings optional) |
| Edge | Declared store dependency (e.g. `07_grounds` → `grounds.yml` → `07_part_b`) |
| Expanded node | That stage’s parameter keys from `_data/<stage>/parameters.yml`, with current values |
| Checkbox on a parameter | Include this knob as a multiverse **axis** (or as a member of a stage-level axis) |
| Checkbox on a node | Include the **whole stage** (expand to its declared multiverse-eligible knobs, or mark the stage for a typed refit) |

The graph is a view of the analysis-as-done, not a second workflow
engine. Running the product still goes through a PopulateButton that
reads the selection store.

### Selection store (source of truth)

Do **not** mutate every stage’s `parameters.yml` when ticking boxes.
Write a study-local selection document, e.g.:

```yaml
# _data/11_multiverse/axes.yml  (or analysis_axes.yml under corpus/)
- index: dialogue-v1
  include_stages: []          # e.g. ["07_part_b"]
  include_parameters:
    - stage: 07_part_b
      key: experience_bases
    - stage: 07_part_b
      key: n_boot
  # Phase 1 executable axes map onto run_analysis_multiverse kwargs:
  experience_definitions: true
  weightings: true
  exclusions: true
  quote_thresholds: true
  rounds: true
```

Canonical paper axes may be represented either as first-class flags
(above) or as curated `include_parameters` entries that the Phase 1
runner understands. The UI must show **cost class** per tick
(see below) so “whole `03_vq`” cannot look like a free checkbox.

### Cost classes (required for honesty)

Every selectable item carries one of:

| Class | Meaning | Example |
|-------|---------|--------|
| `aggregate` | Re-read main-run codes / packed stores; no LLM; product over estimators | experience definition, document weights, round split |
| `refit` | Re-run non-LLM fit chain; invalidate downstream Address | `n_vq` ⇒ 03 → 04 → 06 |
| `llm` | Model calls; budgeted; not silent cartesian explosion | extract / grounds / naming |
| `display` | Not an analysis axis (UI-only) | walk speed, markdown copy |

Phase 1 only **executes** `aggregate` ticks that map to
`run_analysis_multiverse`. `refit` / `llm` ticks may be shown and
stored as intent, but the Run button refuses them (or runs only the
aggregate projection) until Phase 2 declares handlers.

### How the DAG is built

Prefer **explicit study metadata** over guessing from YAML:

```yaml
# Option A — on 11_multiverse or _data/corpus/pipeline.yml
pipeline:
  nodes:
    - id: 01_chunk
      permalink: /01_chunk/
      parameters: _data/01_chunk/parameters.yml
    - id: 07_grounds
      permalink: /07_grounds/
    - id: 07_part_b
      permalink: /07_part_b/
  edges:
    - from: 01_chunk
      to: 02_extract
      via: _data/corpus/chunks.yml
    - from: 07_grounds
      to: 07_part_b
      via: _data/corpus/grounds.yml
```

Option B (current): discover edges from declared interface stores
(`input` / `data` / `output` / `pack` / Class B sidecars) via
`discover_pipeline_edges`, composed by `compose_pipeline_manifest`.
Topology is automatic; no handwritten `edges:`.

### Map chrome is a product, not a magic overlay

After Option B, `_data/corpus/pipeline.yml` still duplicated two
kinds of information. Split them:

| Kind | Examples | Owner |
|------|----------|--------|
| **Identity** | `title`, `permalink`, which parameters file | **Original stage** frontmatter / `parameters:` store — already on each referia; discovery reads it |
| **Interpretation** | `cost_class`, `multiverse_eligible`, `paper_axis`, picker labels | **Map / multiverse product** — how *this study’s* analysis-choice view treats knobs |

Do **not** put interpretation knobs onto every upstream
`parameters.yml` (that couples `03_vq` to multiverse concerns).
Do **not** keep a magical corpus-side `pipeline.yml` outside the
store model (CIP-0024).

**Insert a referia between discovery and consumers** (hub and
`11_multiverse`): a thin map stage (hub `/`, or a dedicated
`00_map` / extend `11_multiverse`) whose **output** is a declared
store such as `pipeline_meta.yml` listing, per stage id, only the
interpretation chrome. Hub and multiverse **declare** that store as
input; `compose_pipeline_manifest` merges discovery topology +
identity from stage metas + interpretation from the declared
product. Retire `_data/corpus/pipeline.yml`.

### Interaction model (referia)

Reuse CIP-0011 patterns where possible:

1. **Viewer**: `PlotlyFigure` (or a small dedicated `PipelineDag`
   viewer type if click/expand outgrows Plotly) showing the DAG.
   Node click sets a bound review field `focus_stage`.
2. **Review panel**: when `focus_stage` is set, render that stage’s
   parameter list with `Checkbox` rows bound into the selection
   store (HTMX field updates, same as other review widgets).
3. **Stage-level checkbox** at the top of the expanded panel.
4. **Run** stays a `PopulateButton` calling
   `run_analysis_multiverse` with `row_args` read from the selection
   store (not only from `parameters.yml` seed/n_jsd_shuffles).

If Plotly click → expand is too awkward for checkboxes, Phase 1 may
use a **two-pane** layout: left = static/HTML DAG (or Plotly for
overview only), right = stage accordion with checkboxes. The CIP
requires the connected view and the ticks; it does not require a
single widget to do both on day one.

### Mapping ticks → `run_analysis_multiverse` (Phase 1)

CIP-001E’s product already encodes the paper axes. Phase 1 UI
checkboxes toggle which of those axes are **active** in the product
(default: all five on, matching today’s behaviour). Extending the
compute to accept an `axes=` / selection dict is part of this CIP;
behaviour with all aggregate paper axes selected must match the
current 216-config main-run product (up to seed).

Whole-stage tick on `07_part_b` in Phase 1 means: include all
**aggregate** knobs declared eligible on that stage (experience
bases, bootstrap, min_gap, …) that the runner knows how to product.
It does **not** mean re-classify grounds.

### Phase 2 (declared; not required to close Phase 1)

1. Eligible `refit` recipes as named graphs (e.g. `vq_k_refit`:
   vary `n_vq` ∈ {25,40,60}, replay 03→04→06).
2. Optional coding-source axis when a recode store exists (paper’s
   path from 216 → 1080) — still not 1080 LLM jobs from one tick.
3. Generic Option B edge discovery — **done** (`compose_pipeline_manifest` / declared sidecars; edges no longer handwritten).
4. **Map chrome as declared product** (next):
   - Identity only from stage frontmatter (drop title/permalink
     duplication from any overlay file).
   - Interpretation (`cost_class` / `multiverse_eligible` /
     `paper_axis`) written by a map referia to a declared store;
     hub + `11_multiverse` consume it; delete
     `_data/corpus/pipeline.yml`.
   - Hub `/` shows the discovered DAG (click → permalink); multiverse
     keeps click → `focus_stage`.

### Out of scope

- Automatic cartesian products over LLM stages from a stage tick
- Editing upstream `parameters.yml` values from the multiverse page
  (selection is “vary among declared levels”, not “change the main run”)
- Replacing GAP.md / METHODS_MAP.md (those stay documentary; the DAG
  should link to them, not duplicate the paper grain story)

### Tenets

Aligns with progressive augmentation (extend referia viewers/compute;
do not fork lynguine), pragmatic automation (only automate axes that
help the human robustness question), and template-driven composition
(declare pipeline + eligible knobs once; instantiate the product).

## Implementation Plan

1. **Study pipeline manifest** — Phase 1 Option A `pipeline.yml`
   (nodes/edges/cost); superseded for *edges* by Option B discovery.
2. **Selection store + compute** — axis filter on
   `run_analysis_multiverse`; persist under `_data/11_multiverse/`.
3. **Viewer + checkboxes on `11_multiverse`** — DAG + focus-stage
   param table; Phase 1 refuses refit/llm.
4. **Option B discovery** — `discover_pipeline_edges` +
   `compose_pipeline_manifest`; formats study drops handwritten edges.
5. **Map chrome product** (Phase 2 item 4)
   - Map referia writes declared `pipeline_meta` (interpretation only).
   - Compose: discovery + frontmatter identity + meta product.
   - Hub DAG with permalink navigation; delete corpus `pipeline.yml`.
6. **Tests / docs** — selection → product; discovery golden;
   meta-store compose; GAP / METHODS_MAP pointers.

## Backward Compatibility

- Studies without a pipeline manifest keep today’s
  `11_multiverse` PopulateButton behaviour (full aggregate product).
- Existing `parameters.yml` files are unchanged by ticking.
- No change to path-mode thesis trees unless they opt into a
  multiverse page + manifest.

## Testing Strategy

- Unit: selection document → axis product cardinality; eligibility
  filter; cost-class gate.
- Unit: `run_analysis_multiverse` with subset of axes (e.g. definition
  only) returns a smaller product and stable markdown.
- Smoke (formats study): `/11_multiverse/` loads with empty/main-run
  stores; DAG render does not require LLM keys.
- Manual: tick/untick, Save, Run, confirm `analysis_multiverse.yml`
  and on-page markdown.
