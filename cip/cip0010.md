## Summary

Make the referia root page (and intermediate directory overviews) driveable by an **ordinary** `_referia.yml` — the same dialect as any review — that **discovers** descendant configs as tall allocation rows and presents them as **one browser-style page** (today’s directory listing behaviour), instead of always using the hardcoded filesystem listing from CIP-000C.

There is **no** special product mode (no `mode: catalog`). Authors compose lynguine primitives: recursive `yaml_directory` (CIP-000F) wrapped in `wide_flatten` (CIP-0010 Pattern A), tall scores output, Liquid viewer, and optional `filters:`. Root `GET /` loads `{root}/_referia.yml` when present; otherwise falls back to CIP-000C listing.

**Presentation (Accepted model):** recreate the current browser with lynguine’s **Pattern A** — tall discovery + tall writable scores remain the authoritative store; Liquid and wide field names are a **view** (`flattenKeys` + index-augmented names / virtual get/set). Do **not** replace the scores DataFrame with a materialized wide row for Save. Liquid list bodies use `rows` (`row.<column>`); Pattern A keeps widgets/Save on the tall store.

The config follows access–assess–address: **input** discovers configs (title, description, date, path); **output** holds writable assessments. v1 progress flag is **`complete`** (incomplete ≈ old leaf `current: true`). Leaf YAML `current:` stays legacy for CIP-000C listing until a later migration removes it.

Separately, add a **general, config-declared filter bar** (tristate booleans, date ranges, categoricals) under `.panel-nav`, collapsible, default **cleared**.

Extends [REQ-0009](../requirements/req0009_multi-config-web-hosting.md), [REQ-000D](../requirements/req000D_singleton-navigation-chrome.md), [REQ-000E](../requirements/req000E_named-layout-compositions.md) (named layouts — Markdown/LaTeX-style, not Word placement), and [CIP-000C](./cip000C.md). Depends on lynguine [REQ-000C](https://github.com/lawrennd/lynguine/blob/main/requirements/req000C_explicit-singleton-index.md) for named singleton wrapping `index`.

## Motivation

The OneDrive referia tree holds hundreds of `_referia.yml` files clustered into seasonal work. Today:

- Leaf configs expose listing meta (`title`, `description`, `date`, `current`).
- Root `GET /` always runs `_list_sub_configs` → `_render_directory_listing` and **never loads** `{root}/_referia.yml`.
- A parent `_referia.yml` replaces the child listing with a full review — discovery-based overviews cannot compose at `/` without this CIP.
- Listing helpers duplicate discovery outside allocation.

We want seasonal/events overviews as ordinary `_referia.yml`: same dialect, Liquid viewer, same server. lynguine CIP-000F supplies rows; lynguine CIP-0010 supplies the one-page / wide-view contract; this CIP makes `/` serve that config and keeps Save on tall `complete`.

## Detailed Description

### Layering

| Layer | Responsibility |
|-------|----------------|
| lynguine CIP-000F | Recursive `yaml_directory` + `fields` → one meta row per config file |
| lynguine CIP-0010 | Wide view / `flattenKeys` / virtual get/set over tall store (Pattern A); optional materialized flatten + unflatten |
| referia CIP-0010 (this) | Root `GET /` loads `{root}/_referia.yml` when present; ordinary config using `wide_flatten` + tall scores; Pattern A for browser-like Liquid; writable `complete`; general filter bar; CIP-000C listing fallback; retire leaf `current` later |

Aligns with progressive augmentation, explicit–implicit separation, and lynguine’s authoritative-store-and-views tenet.

### No special mode

Configs are ordinary `_referia.yml`. Discovery vs single-candidate review is expressed by **input shape** (`wide_flatten` over `yaml_directory` vs excel/csv/…), not by a referia `mode` flag. Do not introduce `mode: catalog` or equivalent product switches.

### Singleton / implied index after `wide_flatten`

Materialized `wide_flatten` yields **one row**. Today lynguine sets that row’s index to a bare `RangeIndex` (`0`) — there is no config knob for the label.

**Needed (lynguine CIP-0010 / REQ-000C):** wrapping `index` names the **singleton result** (same key as `stack` / `local`). Tall identity before flatten lives on the nested specification (or tall frame), not under a synonym such as `result_index`:

```yaml
input:
  type: wide_flatten
  index: root                 # singleton label of the wide result
  specifications:
    # tall key (e.g. configPath) declared nested / on the tall frame
    type: yaml_directory
    # ...
```

Defaults if omitted: keep today’s `0` for legacy, but new overview configs must set wrapping `index` explicitly. The label matters for Liquid/`get_index()`, output joins that still speak “current index”, and any UI that shows the index name.

**Referia:** the overview config sets wrapping `index` (e.g. `root` or a short title slug). Tall scores remain keyed by `configPath` / `flattenKeys` entries — the singleton index is the **overview record**, not each discovered config.

### Index selector chrome (REQ-000D) — not list filters

In a normal candidate review the UI shows a **record picker** (which thesis / which row am I on?). That is the “index selector.” After `wide_flatten` the overview is **one** data point (`index: root`), so that picker is useless clutter and should hide by default (REQ-000D).

That chrome is **unrelated** to filtering the discovery list. List filter/sort (below) act on tall columns behind the flatten view; they do not “select the current index.”

**Optional author override** (only if someone wants the singleton picker visible anyway — rare):

```yaml
navigation:
  index: auto          # auto | show | hide  (default auto = hide when ≤1)
  subindex: auto
```

v1 can ship **infer-only** (`auto`); explicit `show`/`hide` satisfies REQ-000D’s override criterion when convenient. Do not invent a catalog mode for this.

### Layout compositions (named kinds — not Word placement)

Today’s web chrome hardcodes **document-centric** side-by-side panes (`.two-col`: viewer | review). That fits theses and PDFs. It does **not** fit a discovery overview: a path list in the left pane and an empty review column wastes the frame. Overview assessments belong **beside each entry** (mark in place).

**Requirement:** [REQ-000E](../requirements/req000E_named-layout-compositions.md) — authors choose among a **small set of named layout compositions**, like a Markdown/LaTeX document class. They do **not** get fine geometry (no region coordinates, desktop-publishing knobs, or per-widget absolute placement).

**v1 named set (sketch — expand deliberately, not unboundedly):**

| Name | Intent | Typical use |
|------|--------|-------------|
| `side_by_side` | Viewer column + review column (today’s default) | Document / thesis review |
| `inline_list` | Single list; each row shows identity + inline assessment widgets | Discovery overview / seasonal catalog |
| *(later)* `stacked`, `viewer_only`, … | Only when a real workflow needs them | — |

Config sketch (ordinary `_referia.yml`, any review):

```yaml
display:
  layout: inline_list   # side_by_side (default) | inline_list | …

viewer:
  - liquid: |
      {# row identity / chrome — rendered in the list composition #}
      <a href="{{ config_url }}">{{ title }}</a>
      <span class="meta">{{ date }}</span>

review:                   # field mapping — same dialect as today
  - field: complete
    type: Checkbox
  - field: category
    type: Dropdown
    args:
      options: [season, marking, thesis, other]
```

**Field mapping is ordinary `review:` (not a new widget type).**

Authors already declare which fields appear and as which controls via `review:` (`field` + `type` + optional `args`). Under `inline_list`, that same list is the **per-row assessment strip**; under `side_by_side` it remains the right-hand form. `viewer:` supplies read-only chrome (Liquid / display) — for `inline_list`, that chrome is composed **into each row** (or as list header + per-row fragments), not into a vacant sibling pane.

We do **not** invent a new reviewing block type (e.g. `type: InlineListRow`) for field mapping. Layout chooses *composition*; `review:` / `viewer:` remain *content*. Clusters already in the dialect (`Section`, `group`, templates) may still expand inside `review:` if a row needs grouped controls — that is reuse, not a new layout API.

**`inline_list` behaviour (this CIP’s overview HOW):**

- **Web-first only** for named layouts (see scope below).
- No vacant second pane; one composition fills the panel under `.panel-nav` (+ filter bar).
- Each visible tall key (from filtered `flattenKeys` / `rows`) renders as a row: viewer chrome **and** the `review:` widgets for that key’s tall scores via Pattern A get/set.
- Save still writes the **tall** store.

**Surface scope: web-first**

- Implement `display.layout` and both v1 compositions on the **web** path (`WebReviewer`, `review_panel.html`, `render.py`).
- Jupyter (`Reviewer` / ipywidgets) is **out of scope** for named layouts in this CIP — no parity requirement. Notebook authors keep today’s one-row-at-a-time display until a separate decision on the Jupyter display surface (see backlog: evaluate retiring Jupyter for display).
- Unknown layout names: fail clearly at config load / panel render (do not silently fall back without a log).

**What we are not doing for layout**

- Not a freeform page builder or Word-like placement UI.
- Not inventing `mode: catalog` — layout is a named composition; input shape still decides discovery vs candidates.
- Not exposing CSS grid/flex recipes in `_referia.yml`.
- Not a new `review:` widget/`type` whose job is “be a list row”.
- Not Jupyter layout parity in this CIP.

### Presentation model (browser = one page, tall store)

**Problem.** Default referia UI is **one row at a time**. Today’s directory listing is **one view of the whole tree**. Discovering ~285 configs must not mean paging 285 single-config pages.

**Accepted solution — tall store + flatten view (Pattern A), list Liquid via `rows`:**

1. **Allocation (000F):** tall frame — one row per discovered `_referia.yml` (projected fields + `store_fields` paths). Discovery starts at a directory but **lists only configs under subdirectories**, not the overview file in that directory itself (see *Descendants-only discovery*).
2. **Join output:** tall scores (`complete`, `category`, …) on stable path/key (`configPath` or equivalent).
3. **Filter + sort bar:** operate on **tall column names** that the flatten exposes in the list (`title`, `date`, `complete`, …) — see *Filter and sort bar*. There is no “current index” to rebind when the set shrinks.
4. **Views over that tall set:**
   - **`rows` (Liquid list authoring):** ordered list of mappings for the filtered+sorted tall working set — `row.title`, `row.date`, `row.complete`, `row.config_url`, …. This is how overview / `inline_list` templates read fields.
   - **Pattern A (store / widgets):** `flattenKeys` + virtual get/set `"{key}{sep}{field}"` → tall `(index=key, column=field)` so Save and per-row widgets do not materialize a wide scores sheet. `flattenKeys` order matches `rows` order after filter/sort.
5. **Edit assessments:** `review:` widgets in each `inline_list` row bind to the tall store for that row’s key. Never persist a wide scores sheet as the default.
6. **Navigate to child:** link to that config’s URL (`/applications/…/`), not an index step that replaces the overview.

#### Liquid field access (decision)

The flatten gives **structure**: many tall rows, shared column names, one overview wrapper (`index: root`). Authors must not need to invent `key||title` strings in Liquid.

| Audience | How to read a field | Example |
|----------|---------------------|---------|
| Overview / list Liquid | `rows` — one mapping per tall row | `{{ row.title }}`, `{{ row.complete }}` |
| Per-row widgets / Save | Pattern A virtual get/set on tall store | field `complete` for key `applications/…/_referia.yml` |
| Wide singleton (rare) | `flattenKeys` + composed names if a template truly needs the flat dict | implementation detail; not the default authoring guide |

```liquid
{% for row in rows %}
  <li>
    <a href="{{ row.config_url }}">{{ row.title }}</a>
    <span>{{ row.date }}</span>
  </li>
{% endfor %}
```

So: **filters/sort talk column names; Liquid list bodies talk `row.<column>`; widgets talk `review:` fields on the tall key.** Pattern A is the machinery underneath, not the author-facing Liquid dialect for lists.

**What we are not doing (default path)**

- Not making materialized `wide_flatten` the authoritative scores DataFrame (Pattern B) — schema churn; needs `wide_unflatten` on every Save.
- Not treating series/`entries` under a fake parent index as the primary overview model (series hardening is a separate CIP).
- Not keeping default one-at-a-time browsing as the primary chrome for discovery overviews.
- Not adding a special `mode` flag to distinguish “catalog” from “review”.
- Not requiring authors to write separator-joined wide names in ordinary overview Liquid.

| Concept | Candidate review (typical) | Discovery overview (this CIP’s example) |
|---------|---------------------------|----------------------------------------|
| What `input` rows mean | Candidates / theses / … | Discovered configs (tall) |
| Authoritative store | Current index row + output | Tall discovery ⋈ tall scores |
| Layout composition | `side_by_side` (default) | `inline_list` (REQ-000E) |
| Primary UI | Viewer + form for current index | One-page list (`rows` + inline widgets) + filter/sort bar |
| Edit progress | Output widgets on current row | Tall get/set **in the row** for that key’s `complete` |
| Open child review | n/a | Link to child config URL |

### Writable assessments (`complete` as output)

Leaf `current: true|false` is static YAML for the hardcoded listing. Overview progress is an **assessment** in **output**.

**v1 field: `complete` (not `current`).**

| Intent | Leaf YAML today | Tall output (v1) | Tristate filter |
|--------|-----------------|------------------|-----------------|
| Active / in progress | `current: true` | `complete: false` (or unset) | `complete` → false |
| Done / archived | `current: false` or absent | `complete: true` | `complete` → true |
| No constraint | listing `current=0` | — | `complete` → any (cleared) |

| Stage | Source | Fields (examples) |
|-------|--------|-------------------|
| **input** (read-only) | Recursive `yaml_directory` + projection (inside `wide_flatten`) | `title`, `description`, `date`, path via `store_fields` — leaf `current` not authoritative |
| **output** (writable, **tall**) | Scores store (yaml or csv) | `complete`, later `category`, notes |
| **view** | lynguine CIP-0010 Pattern A | `flattenKeys` + wide names for Liquid / optional widgets |

**Join / index:** Stable identity from discovery (relative path / `configPath`). Output merges onto that index on load.

**Seeding (optional, explicit):** On first encounter, compute may set `complete: false` when leaf `current: true`. After that, **output wins**. No write-back into leaf `_referia.yml` in v1.

### Retire leaf `current` (later)

1. **Now:** Overview configs use output `complete`; legacy listing may still read leaf `current`.
2. **Migration backlog:** Stop writing leaf `current`; seed scores; listing ignores leaf `current` or joins scores.
3. **Cleanup:** Delete leaf `current:` keys; drop listing dependence; docs/tests updated.

### Root `GET /` behaviour

In `--root` mode:

1. If `{root}/_referia.yml` exists → serve it as an ordinary config (same pipeline as any other `_referia.yml`).
2. Else → today’s `_render_directory_listing` (CIP-000C fallback).

Legacy listing query form (`after` / `before` / `current`) remains for fallback only. Filtering on a loaded root config uses the general filter bar.

### Descendants-only discovery (exclude the overview directory’s own file)

The overview `_referia.yml` lives in the directory it discovers. Recursive `**/_referia.yml` would otherwise include **itself**.

**Decision:** discovery is configured to list configs in **subdirectories only**, not files sitting in the start directory.

```yaml
source:
  - directory: .
    glob: "**/_referia.yml"
    recursive: true
    include_start_directory: false   # NEW (lynguine) — only paths under child dirs
```

- `include_start_directory: true` (default) — today’s behaviour (matches in `.` and below).
- `include_start_directory: false` — skip matches whose parent directory is the source `directory` itself; keep everything nested underneath.

This is a **lynguine directory-reader option** (generic; not referia-specific). Referia overview configs set it false. No post-hoc “exclude self by path” compute required for the common case.

### Filter and sort bar (tall columns behind the flatten view)

First-class web feature — not overview-only. For discovery overviews it is the control surface for the list.

**Mental model:** `wide_flatten` does not erase the tall table. There is still a set of rows with shared **column names** (`title`, `description`, `date`, `complete`, `category`, … — input projections plus joined output). Filter and sort declare those column names. They shrink and order that tall set; `rows` / `flattenKeys` are views of the result.

There is **no current index** in this UI. Nothing “moves selection” when filters change — the list simply shows the surviving rows in sort order. (Candidate reviews that still use a record picker are a separate chrome concern; filter/sort on a multi-row index can reuse the same column machinery later.)

**Placement:** Under `.panel-nav` in `review_panel.html`, collapsible. **Default = clear** (no filter constraint, default sort or config-declared default). **Clear** restores that state.

```yaml
filters:
  - field: complete          # tall column (joined output)
    type: boolean            # tristate: any / true / false
    label: Complete
  - field: date              # tall column (from discovery projection)
    type: date_range
    label: Date
  - field: category
    type: categorical
    label: Status
    values: [red, amber, green]

sort:
  - field: date              # tall column
    order: desc              # asc | desc
  # optional secondary keys…
```

| Control | UI | Effect on tall set |
|---------|----|--------------------|
| `boolean` | Tristate: any / true / false | Keep rows matching; null ≠ true/false unless coalesced in compute |
| `date_range` | after + before | Inclusive ISO bounds on that column |
| `categorical` | multi-select / chips | Empty = no constraint |
| `sort` | field + direction (multi-key allowed) | Orders remaining rows → `rows` / `flattenKeys` order |

**Behaviour:** Unknown filter/sort fields warn at load. Shareable query params where practical. Same column names authors use in `row.<field>` and in `wide_flatten.columns` / `output.columns`.

### Example root `_referia.yml` (sketch)

```yaml
referia_config_version: 2
title: "Referia — seasonal work"
description: "Overview of review configs by time of year."
date: 2026-10-11

# Explicit flatten: tall discovery inside wide_flatten (lynguine CIP-0010).
# Scores stay tall (Pattern A); do not put `complete` in wide `columns`.
input:
  type: wide_flatten
  separator: "||"
  order: index_then_field
  index: root                  # singleton wide-row label (lynguine REQ-000C)
  keys_field: flattenKeys
  columns:
    - title
    - description
    - date
    - config_url
  specifications:
    type: yaml_directory
    # tall identity: configPath column / index before flatten (nested)
    source:
      - directory: .
        glob: "**/_referia.yml"
        recursive: true
        include_start_directory: false   # descendants only — not this overview file
    fields:
      - title
      - description
      - date
    store_fields:
      directory: sourceDirectory
      filename: sourceFile
      root: sourceRoot
    # compute: configPath, config_url

output:
  type: yaml                 # or csv — prefer text scores over xlsx for overviews
  index: configPath
  filename: overview-scores.yml
  directory: ./info
  columns:
    - complete
    - category
    - notes

review:
  - type: checkbox
    field: complete
    args:
      description: Complete
  - type: select
    field: category
    args:
      options: ["", red, amber, green]
      description: Status

filters:
  - field: complete
    type: boolean
    label: Complete
  - field: date
    type: date_range
    label: Config date
  - field: category
    type: categorical
    label: Status
    values: [red, amber, green]

sort:
  - field: date
    order: desc

viewer:
  - liquid: |
      ## Incomplete (active work)
      {% for row in rows %}
        {% unless row.complete %}
      - [{{ row.title }}]({{ row.config_url }}) — {{ row.date }}
        {% endunless %}
      {% endfor %}
      ## All (filtered + sorted set)
      {% for row in rows %}
      - [{{ row.title }}]({{ row.config_url }})
      {% endfor %}
```

Liquid list bodies use **`rows`** (`row.<column>`). Pattern A keeps Save/widgets on the tall store.

Event windows live in this config as `constants`, a small YAML input, or Liquid — **not** `_events.yml`.

## Implementation Plan

1. **Dependency**
   - Pin/bump lynguine to CIP-000F + CIP-0010; confirm Pattern A APIs in referia’s environment.

2. **Presentation for discovery overviews**
   - Filter + sort tall columns → ordered working set.
   - Liquid `rows` (`row.<column>`) for list/overview templates; Pattern A virtual get/set for per-row widgets / Save.
   - `inline_list` layout; child open via URL.

3. **Root routing**
   - `index()` with `app.state.root`: load `{root}/_referia.yml` when present; else CIP-000C listing.
   - Tests: root with discovery config; no-config listing; ordinary non-discovery root review.

4. **General filter + sort bar**
   - `filters:` + `sort:` on tall column names; collapsible UI; default clear; tests including tristate and multi-key sort.

5. **Example + docs**
   - Minimal root `_referia.yml` (`wide_flatten` + tall yaml/csv scores); exclude-self; document Pattern A vs `rows` secondary.

6. **Security**
   - CIP-000E listing/XSS rules; validate filter query params; paths under serve/allowed roots.

7. **Follow-up backlog (after v1)**
   - Retire leaf `current:`; seed/cleanup.

## Backward Compatibility

- No root `_referia.yml` → CIP-000C listing unchanged.
- Configs without `filters:` → no filter bar.
- Ordinary `_referia.yml` at root serves that config at `/` (intentional).
- Leaf `current:` remains for legacy listing until migration.

## Testing Strategy

- Root without `_referia.yml` → listing unchanged.
- Root with ordinary discovery `_referia.yml` (`wide_flatten` + tall scores) → one-page overview of many configs (not bare listing; not one-row-only paging as primary UX).
- `rows` / `flattenKeys` update when filter/sort change; editing `complete` persists **tall** scores and reloads.
- Save must not require `wide_unflatten` on the default path (assert tall output columns).
- Filter bar: tristate / date_range / categorical / clear.
- Intermediate overview parent still links to child config URLs.
- Smoke: OneDrive-style nested tree.
- No `mode:` key required or interpreted for this behaviour.
