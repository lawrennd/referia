## Summary

Make the referia root page (and intermediate directory overviews) driveable by an **ordinary** `_referia.yml` — the same dialect as any review — that **discovers** descendant configs as tall allocation rows and presents them as **one same-page list**, instead of always using the hardcoded filesystem listing from CIP-000C.

There is **no** special product mode (no `mode: catalog`). **lynguine keeps the data results** (recursive `yaml_directory`, tall join, tall Save). **referia chooses how to show them:** `display.layout: inline_list` puts every working-set row on one page (viewer chrome + `review:` widgets per row), with **filter + sort instead of the index selector**. Root `GET /` loads `{root}/_referia.yml` when present; otherwise falls back to CIP-000C listing.

**Presentation (Accepted model — tall-first):**

- **Store:** tall discovery ⋈ tall scores (authoritative). Do not require `wide_flatten` for overviews; keep lynguine flatten/Pattern A available where a true singleton wide snapshot helps other workflows.
- **Display:** `display.layout` (REQ-000E). `inline_list` → inject Liquid `rows` (`row.<column>`), render assessments in-row, hide record picker, show filter/sort bar.
- **get/set:** still tall `set_index(key)` + `set_value(field)` per widget; chrome stops pretending there is one “current” candidate.

The config follows access–assess–address: **input** discovers configs; **output** holds writable assessments. v1 progress flag is **`complete`**. Leaf YAML `current:` stays legacy for CIP-000C listing until a later migration removes it.

Extends [REQ-0009](../requirements/req0009_multi-config-web-hosting.md), [REQ-000D](../requirements/req000D_singleton-navigation-chrome.md), [REQ-000E](../requirements/req000E_named-layout-compositions.md), and [CIP-000C](./cip000C.md).

**Design checkpoint:** pre-shift docs committed as `37ed710` (named layouts / rows / filter-sort on tall columns still framed around flatten). This revision is the tall-first same-page shift.

## Motivation

The OneDrive referia tree holds hundreds of `_referia.yml` files clustered into seasonal work. Today:

- Leaf configs expose listing meta (`title`, `description`, `date`, `current`).
- Root `GET /` always runs `_list_sub_configs` → `_render_directory_listing` and **never loads** `{root}/_referia.yml`.
- A parent `_referia.yml` replaces the child listing with a full review — discovery-based overviews cannot compose at `/` without this CIP.
- Listing helpers duplicate discovery outside allocation.

We want seasonal/events overviews as ordinary `_referia.yml`: same dialect, Liquid viewer, same server. lynguine CIP-000F supplies **tall** discovery rows; referia same-page display lists them; this CIP makes `/` serve that config and keeps Save on tall `complete`.

## Detailed Description

### Layering

| Layer | Responsibility |
|-------|----------------|
| lynguine CIP-000F | Recursive `yaml_directory` + `fields` → one meta row per config file (**keep these results**) |
| lynguine (store) | Tall join, tall Save; optional `wide_flatten` / Pattern A when a workflow truly wants a wide singleton |
| referia CIP-0010 (this) | Root `GET /` loads config; **`display.layout`** chooses same-page list vs side-by-side; `rows` Liquid; filter/sort chrome; writable `complete`; CIP-000C listing fallback |

Aligns with progressive augmentation, explicit–implicit separation, and lynguine’s authoritative-store-and-views tenet.

### No special mode — display option, not product mode

Configs are ordinary `_referia.yml`. Do not introduce `mode: catalog`.

- **What is discovered** = input shape (`yaml_directory` vs excel/… ) — lynguine results.
- **How it is shown** = `display.layout` (and filter/sort) — referia reviewer/viewer chrome.

`inline_list` is the option that “triggers everything to list”: inject `rows`, mark in place, replace the index selector with filter/sort.

### Index selector vs filter/sort (web and Jupyter)

In a normal candidate review (`side_by_side`) the UI shows a **record picker** (which row am I on?). That remains.

Under **`display.layout: inline_list`**:

1. **Hide** the index selector (and useless subseries chrome) — the list *is* the navigation.
2. **Show** the filter + sort bar instead — same tall-column controls on **web and Jupyter**.
3. Widgets still call tall `set_index(key)` + `set_value(field)` under the hood; the user never picks a single “current” row to browse the catalog.

REQ-000D (hide selector when ≤1 choice) still applies for singleton `side_by_side` reviews. List layout is the stronger rule: when listing, selector yields to filter/sort even if many keys exist.

Optional override (rare; any layout):

```yaml
navigation:
  index: auto          # auto | show | hide
  subindex: auto
```

### Layout compositions (named kinds — not Word placement)

Today’s web chrome hardcodes **document-centric** side-by-side panes (`.two-col`: viewer | review). That fits theses and PDFs. It does **not** fit a discovery overview: a path list in the left pane and an empty review column wastes the frame. Overview assessments belong **beside each entry** (mark in place).

**Requirement:** [REQ-000E](../requirements/req000E_named-layout-compositions.md) — authors choose among a **small set of named layout compositions**, like a Markdown/LaTeX document class. They do **not** get fine geometry (no region coordinates, desktop-publishing knobs, or per-widget absolute placement).

**v1 named set (sketch — expand deliberately, not unboundedly):**

| Name | Intent | Typical use |
|------|--------|-------------|
| `side_by_side` | Viewer column + review column (today’s default) | Document / thesis review |
| `inline_list` | Single list; each row shows identity + inline assessment widgets | Discovery overview / seasonal catalog |
| *(later)* `stacked`, `viewer_only`, … | Only when a real workflow needs them | — |

**Interactive figures (CIP-0011):** do **not** require a new layout name for v1. Subject-facing plots are typed entries under `viewer:` (e.g. `PlotlyFigure`) that share the field store with `review:` under existing compositions (typically `side_by_side`). The novelty is the viewer contract (opt-in interaction + propagation), not composition. A dedicated third region (prose \| plot \| form) is only a later layout option if stacking viewer entries fails — see [CIP-0011](./cip0011.md) / [REQ-000F](../requirements/req000F_interactive-viewer-components.md).

Config sketch (ordinary `_referia.yml`, any review):

```yaml
display:
  layout: inline_list   # triggers same-page list chrome

viewer:
  - liquid: |
      {% for row in rows %}
      <a href="{{ row.config_url }}">{{ row.title }}</a>
      <span class="meta">{{ row.date }}</span>
      {% endfor %}

review:                   # field mapping — same dialect as today; rendered per row
  - field: complete
    type: Checkbox
  - field: category
    type: Dropdown
    args:
      options: [season, marking, thesis, other]

filters: …                # replaces index selector under inline_list
sort: …
```

**Field mapping is ordinary `review:` (not a new widget type).**

Under `inline_list`, that list is the **per-row assessment strip**; under `side_by_side` it remains the right-hand form. `viewer:` supplies subject-facing chrome (historically read-only Liquid; CIP-0011 allows opt-in interactive entries) — for `inline_list`, Liquid sees **`rows`** built from the filtered+sorted tall working set (lynguine results, referia view).

We do **not** invent a new reviewing block type for field mapping. Layout chooses *composition*; `review:` / `viewer:` remain *content*.

**What `inline_list` triggers (the “list everything” option):**

| Chrome | `side_by_side` (default) | `inline_list` |
|--------|--------------------------|---------------|
| Index selector | Shown when ≥2 choices (REQ-000D) | Hidden — list is navigation |
| Filter + sort bar | Optional / when configured | Primary navigation chrome |
| Viewer | Current-row mapping | `rows` list-of-dicts (+ optional header) |
| Review widgets | One form for focus row | Same specs, once per visible row |
| Surfaces | Web + Jupyter (as today) | Web + Jupyter (filter/sort + list) |

Save still writes the **tall** store. Unknown layout names: fail clearly at load/render.

**What we are not doing for layout**

- Not a freeform page builder or Word-like placement UI.
- Not inventing `mode: catalog`.
- Not exposing CSS grid/flex recipes in `_referia.yml`.
- Not a new `review:` widget/`type` whose job is “be a list row”.
- Not requiring authors to use `wide_flatten` or separator-joined Liquid names for overviews.

### Presentation model (browser = one page, tall store)

**Problem.** Default referia UI is **one row at a time**. Today’s directory listing is **one view of the whole tree**. Discovering ~285 configs must not mean paging 285 single-config pages.

**Accepted solution — lynguine tall results + referia same-page list:**

1. **Allocation (000F):** tall frame — one row per discovered `_referia.yml`. **Descendants-only** (`include_start_directory: false`) so the overview file is not listed.
2. **Join output:** tall scores on stable path/key (`configPath`).
3. **`display.layout: inline_list`:** referia builds the page from that tall working set — not a lynguine reshape for presentation.
4. **Filter + sort:** tall column names (`title`, `date`, `complete`, …); replace the index selector under list layout (web + Jupyter).
5. **Liquid `rows`:** ordered list of mappings after filter/sort — `row.title`, `row.complete`, ….
6. **Widgets:** `review:` specs rendered per visible row; each update is tall `set_index(key)` + `set_value(field)`.
7. **Child link:** URL to that config (`/applications/…/`).

Optional: `wide_flatten` / Pattern A remain in lynguine for other uses; **not** the overview authoring path.

#### Liquid field access (decision)

| Audience | How to read a field | Example |
|----------|---------------------|---------|
| List Liquid | `rows` from tall working set | `{{ row.title }}` |
| Per-row widgets / Save | Tall focus get/set | `complete` on that key |
| Wide singleton (optional) | lynguine flatten — not required here | — |

**What we are not doing (default path)**

- Not requiring `wide_flatten` for seasonal overviews.
- Not a special Liquid dialect over separator-joined wide names.
- Not Pattern B wide scores as the Save shape.
- Not `mode: catalog`.
- Not keeping one-at-a-time browsing as the primary overview chrome.

| Concept | Candidate review (typical) | Discovery overview (this CIP’s example) |
|---------|---------------------------|----------------------------------------|
| What `input` rows mean | Candidates / theses / … | Discovered configs (tall) |
| Authoritative store | Current index row + output | Tall discovery ⋈ tall scores |
| Layout composition | `side_by_side` (default) | `inline_list` — list option on display |
| Primary UI | Viewer + form + index selector | Same-page list + filter/sort (no selector) |
| Edit progress | Output widgets on current row | Tall get/set **in the row** for that key’s `complete` |
| Open child review | n/a | Link to child config URL |

### Writable assessments (`complete` as output)

Leaf `current: true|false` is static YAML for the hardcoded listing. Overview progress is an **assessment** in **output**.

**v1 field: `complete` (not `current`).**

| Intent | Leaf YAML today | Tall output (v1) | Tristate filter |
|--------|-----------------|------------------|-----------------|
| Active / in progress | `current: true` | `complete: false` (or unset) | `complete` → false |
| Done / archived | `current: false` or absent | `complete: true` | `complete` → true |
| No constraint | listing `current=0` | — | `complete` → any (cleared) |

| Stage | Source | Fields (examples) |
|-------|--------|-------------------|
| **input** (read-only) | Recursive `yaml_directory` + projection | `title`, `description`, `date`, path via `store_fields` — leaf `current` not authoritative |
| **output** (writable, **tall**) | Scores store (yaml or csv) | `complete`, later `category`, notes |
| **view** | referia `rows` / `inline_list` | Liquid `row.<column>` + per-row widgets over tall results |

**Join / index:** Stable identity from discovery (relative path / `configPath`). Output merges onto that index on load.

**Seeding (optional, explicit):** On first encounter, compute may set `complete: false` when leaf `current: true`. After that, **output wins**. No write-back into leaf `_referia.yml` in v1.

### Retire leaf `current` (later)

1. **Now:** Overview configs use output `complete`; legacy listing may still read leaf `current`.
2. **Migration backlog:** Stop writing leaf `current`; seed scores; listing ignores leaf `current` or joins scores.
3. **Cleanup:** Delete leaf `current:` keys; drop listing dependence; docs/tests updated.

### Root `GET /` behaviour

In `--root` mode:

1. If `{root}/_referia.yml` exists → serve it as an ordinary config (same pipeline as any other `_referia.yml`).
2. Else → today’s `_render_directory_listing` (CIP-000C fallback).

Legacy listing query form (`after` / `before` / `current`) remains for fallback only. Filtering on a loaded root config uses the general filter bar.

### Descendants-only discovery (exclude the overview directory’s own file)

The overview `_referia.yml` lives in the directory it discovers. Recursive `**/_referia.yml` would otherwise include **itself**.

**Decision:** discovery is configured to list configs in **subdirectories only**, not files sitting in the start directory.

```yaml
source:
  - directory: .
    glob: "**/_referia.yml"
    recursive: true
    include_start_directory: false   # NEW (lynguine) — only paths under child dirs
```

- `include_start_directory: true` (default) — today’s behaviour (matches in `.` and below).
- `include_start_directory: false` — skip matches whose parent directory is the source `directory` itself; keep everything nested underneath.

This is a **lynguine directory-reader option** (generic; not referia-specific). Referia overview configs set it false. No post-hoc “exclude self by path” compute required for the common case.

### Filter and sort bar (tall columns)

First-class feature (web + Jupyter) — not overview-only. Under `inline_list` it replaces the index selector.

**Mental model:** lynguine still exposes a tall table with shared **column names** (`title`, `date`, `complete`, …). Filter and sort declare those names. They shrink and order the tall set; referia’s `rows` view (and per-row widgets) follow.

Under `inline_list` there is **no current-index browsing**. Nothing “moves selection” when filters change — the list shows surviving rows in sort order. Candidate reviews keep the record picker under `side_by_side`.

**Placement:** Under `.panel-nav` in `review_panel.html`, collapsible. **Default = clear** (no filter constraint, default sort or config-declared default). **Clear** restores that state.

```yaml
filters:
  - field: complete          # tall column (joined output)
    type: boolean            # tristate: any / true / false
    label: Complete
  - field: date              # tall column (from discovery projection)
    type: date_range
    label: Date
  - field: category
    type: categorical
    label: Status
    values: [red, amber, green]

sort:
  - field: date              # tall column
    order: desc              # asc | desc
  # optional secondary keys…
```

| Control | UI | Effect on tall set |
|---------|----|--------------------|
| `boolean` | Tristate: any / true / false | Keep rows matching; null ≠ true/false unless coalesced in compute |
| `date_range` | after + before | Inclusive ISO bounds on that column |
| `categorical` | multi-select / chips | Empty = no constraint |
| `sort` | field + direction (multi-key allowed) | Orders remaining rows → `rows` / `flattenKeys` order |

**Behaviour:** Unknown filter/sort fields warn at load. Shareable query params where practical. Same column names authors use in `row.<field>` and in input/output column lists.

### Example root `_referia.yml` (sketch)

```yaml
referia_config_version: 2
title: "Referia — seasonal work"
description: "Overview of review configs by time of year."
date: 2026-10-11

display:
  layout: inline_list          # same-page list; filter/sort replaces selector

# lynguine tall results — no wide_flatten required
input:
  type: yaml_directory
  index: configPath
  source:
    - directory: .
      glob: "**/_referia.yml"
      recursive: true
      include_start_directory: false
  fields:
    - title
    - description
    - date
  store_fields:
    directory: sourceDirectory
    filename: sourceFile
    root: sourceRoot
  # compute: configPath, config_url

output:
  type: yaml
  index: configPath
  filename: overview-scores.yml
  directory: ./info
  columns:
    - complete
    - category
    - notes

review:
  - type: checkbox
    field: complete
    args:
      description: Complete
  - type: select
    field: category
    args:
      options: ["", red, amber, green]
      description: Status

filters:
  - field: complete
    type: boolean
    label: Complete
  - field: date
    type: date_range
    label: Config date
  - field: category
    type: categorical
    label: Status
    values: [red, amber, green]

sort:
  - field: date
    order: desc

viewer:
  - liquid: |
      ## Incomplete (active work)
      {% for row in rows %}
        {% unless row.complete %}
      - [{{ row.title }}]({{ row.config_url }}) — {{ row.date }}
        {% endunless %}
      {% endfor %}
      ## All (filtered + sorted set)
      {% for row in rows %}
      - [{{ row.title }}]({{ row.config_url }})
      {% endfor %}
```

Liquid list bodies use **`rows`**. Widgets/Save stay on the tall store (lynguine results unchanged).

Event windows live in this config as `constants`, a small YAML input, or Liquid — **not** `_events.yml`.

### Meta schema

| Field | Role |
|-------|------|
| leaf `title`, `description`, `date` | Discovery / input projection |
| tall output `complete`, `category`, … | Writable assessments |
| referia `rows` / `inline_list` | Presentation over tall lynguine results |
| leaf `current` | Legacy CIP-000C listing only |
| `filters` / `sort` | List navigation under `inline_list`; booleans are tristate |

## Implementation Plan

1. **Dependency**
   - Pin/bump lynguine to CIP-000F (+ `include_start_directory` when ready); tall directory results are enough for overviews.

2. **Same-page list presentation (`display.layout: inline_list`)**
   - Filter + sort tall columns → ordered working set; hide index selector.
   - Liquid `rows`; per-row `review:` widgets via tall get/set; web + Jupyter.
   - Child open via URL.

3. **Root routing**
   - `index()` with `app.state.root`: load `{root}/_referia.yml` when present; else CIP-000C listing.
   - Tests: root with discovery config; no-config listing; ordinary non-discovery root review.

4. **General filter + sort bar**
   - `filters:` + `sort:` on tall column names; collapsible UI; default clear; tests including tristate and multi-key sort.

5. **Example + docs**
   - Minimal root `_referia.yml` (tall `yaml_directory` + tall scores + `inline_list`); descendants-only.

6. **Security**
   - CIP-000E listing/XSS rules; validate filter query params; paths under serve/allowed roots.

7. **Follow-up backlog (after v1)**
   - Retire leaf `current:`; seed/cleanup.

## Backward Compatibility

- No root `_referia.yml` → CIP-000C listing unchanged.
- Configs without `filters:` → no filter bar.
- Ordinary `_referia.yml` at root serves that config at `/` (intentional).
- Leaf `current:` remains for legacy listing until migration.

## Testing Strategy

- Root without `_referia.yml` → listing unchanged.
- Root with tall discovery + `inline_list` → one-page overview (not bare listing; not one-row-only paging). A windowed list (CIP-0020) is still a list.
- `rows` update when filter/sort change; editing `complete` persists **tall** scores and reloads.
- Save stays on tall output columns (no wide scores sheet).
- Filter bar: tristate / date_range / categorical / clear.
- Intermediate overview parent still links to child config URLs.
- Smoke: OneDrive-style nested tree.
- No `mode:` key required or interpreted for this behaviour.
