# CIP-0021: Rolling populate-all — batched POST, progress bar, pause

## Summary

Populate-all (Extract all, Embed all, Classify all, Segment all) runs as **rolling batches**. Each HTTP POST computes at most *K* remaining rows, flushes the named cache (CIP-001D), and returns a **progress chip** in `#status-bar`. If work remains and the reviewer has not paused, HTMX immediately POSTs the next batch. Pause replaces that chip with Resume and does not start another batch. Resume is populate-all again: CIP-001D skip-filled does the rest.

This CIP is the interaction CIP-001D called “preferred” and left optional. 001D stays the store contract (skip, flush, do not rebuild the listing). 0021 makes the short POST mandatory for populate-all and adds progress and pause.

Addresses [REQ-0018](../requirements/req0018_rolling-populate-all.md), [REQ-0010](../requirements/req0010_dialogue-pipeline-in-referia.md) (rows on the named cache as they complete), [REQ-0009](../requirements/req0009_multi-config-web-hosting.md) (the worker is free between batches), and [REQ-0013](../requirements/req0013_restartable-review-runtime.md) only at batch boundaries (in-flight LLM cancel is still CIP-001B).

## Motivation

Extract all on 2013 units was one `POST /populate-all/_extract`. The tab waited about an hour, HTMX painted “Request failed,” and the named cache was empty. CIP-001D records that failure and asks for skip + flush so a long POST at least leaves disk state. It also sketched a batch + re-POST loop and parked a progress bar under “SSE later.”

The rolling loop is the small piece. The worker already iterates `working_indices()`. Capping that loop at *K*, returning counts, and letting HTMX fire the same URL again is the existing route with a budget. Pause is “do not fire again.” A job queue, SSE, or extra gunicorn workers are not required for that.

Sleeping the laptop mid-run is then the same as pause: the browser stops chaining; flushed rows stay; the next Extract all is resume.

## Detailed Description

### What 001D still owns

| Piece | Owner |
|-------|--------|
| Skip rows whose populate target is already filled | CIP-001D |
| Flush `cache:` on the LLM cadence | CIP-001D |
| Status fragment, not a rebuilt `inline_list` | CIP-001D |
| Refresh cache as the corpus redo | CIP-001D |
| Listing page size / paged view | CIP-0020 (GET). Populate-all still means the **working set**. |

0021 may ship on top of a 001D that has skip+flush even if 001D’s “survive one long POST after disconnect” never ships. Rolling makes that minimum path unnecessary for LLM populate-all.

### Batch

Each `POST /populate-all/{field}` processes at most *K* rows that still need compute, then returns.

*K* comes from the PopulateButton:

```yaml
- type: PopulateButton
  field: _extract
  args:
    description: Extract
    all: true
    batch: 10          # omit: 10 for LLM-ish, 50 for local
```

Default **10** when omitted. **0** means “this request does the rest” (today’s loop; no chain). Classify all on 07 uses the same key. Segment all can set `batch: 50`.

The route walks `working_indices()` in order, skips filled (001D), runs compute until it has done *K* new rows or the set is exhausted.

### Progress chip

The response targets `#status-bar` (change `render_populate_all_button` from `#review-panel`). Body is a small chip, no phrase text, no paths (CIP-000E):

```
Extracted 40/2013 (0 failed, 12 skipped).  [Pause]
<progress max="2013" value="40">
```

Counts: `n_done` = filled targets after this batch (skip + ok this request + previously filled); `n_total` = `len(working_indices())`; `n_fail` this request; `n_skipped` already filled before this request.

When `n_done < n_total` and not paused, the chip includes:

```html
hx-post="/populate-all/{field}"
hx-trigger="load delay:50ms"
hx-target="#status-bar"
hx-sync="this:replace"
```

`load delay:50ms` is the rolling trigger. No SSE. No second runtime.

When `n_done == n_total`, omit the trigger. Remind Save if explode/pack still need it (CIP-0015). `base.html` “Updating all…” applies only while a batch XHR is in flight.

### Pause and resume

Pause is cooperative at **batch boundaries**. A batch of 10 LLM rows that has already started finishes. Mid-call abort is CIP-001B.

**Pause** (button on the chip) POSTs `/populate-all/{field}/pause` (or the same URL with `pause=1`). The response is the same chip **without** `hx-trigger="load"`, labelled Resume. In-memory on the `WebReviewer` is enough: rolling is one browser chain on one worker. Reloading the page clears the flag; that is also pause.

**Resume** POSTs `/populate-all/{field}` as Extract all does. Skip-filled continues.

Closing the tab, HTMX error, or the machine sleeping: no further `load` events, so no further batches. Disk state is the 001D flush. The reviewer clicks Extract all / Resume.

Do not keep looping in the worker after the batch returns. That would make pause wait until the corpus ends, which is the bug this CIP removes.

### Why this is small

```
POST populate-all/_extract
  for idx in working:          # today: all
      if filled: skip          # 001D
      run_populate
      flush                    # 001D
      if n_this == K: break    # 0021
  return progress chip         # 0021; hx-trigger load if remaining and not paused
```

The Classify/Extract button already posts populate-all. The chip posts the same URL. Pause is a second button that returns the chip without the trigger.

### Alternatives rejected

| Alternative | Why not |
|-------------|---------|
| Job queue (Celery, RQ) | CIP-001D: second runtime; named cache is the store. |
| SSE / streaming one long POST | Still one worker task; pause cannot land until the SSL_read ends; CIP-001D parked this. Rolling POSTs *are* the progress transport. |
| `hx-timeout` only | Fails faster; does not pause; does not flush. |
| True preemption of `run_populate` | CIP-001B. Do not block 0021 on a kernel split. |
| Client-only pause (strip hx-trigger, no server) | Racy with `load delay:50ms`. Server must not start a batch when the last response said pause. Client strip is a welcome extra, not the contract. |

### Non-goals

- Jupyter populate-all chaining (same as 001D unless the Jupyter button shares skip/flush).
- Auto-Save of `output:` explode or pack (still Save).
- Changing compute functions.
- Listing pagination (CIP-0020).

## Implementation Plan

1. **Batch budget** in `_run_populate_all_and_respond`: stop after *K* unfilled rows; return counts; never rebuild the listing (001D).
2. **Progress chip** HTML helper: bar + catalog sentence + Pause/Resume; `hx-trigger="load"` iff remaining and not paused.
3. **`render_populate_all_button`**: `hx-target="#status-bar"`.
4. **Pause route**: set flag; return chip without chain. Resume is populate-all.
5. **`args.batch`**: default 10; `0` = unbounded this request.
6. **Tests**: stub `run_populate` on 25 rows, `batch: 10` → first POST computes 10 and HTML contains `hx-trigger="load"`; pause POST has no load trigger; third POST after two batches computes 5 and has no trigger; skip-filled on resume.

## Backward Compatibility

- Single-row `/populate/{field}` unchanged.
- A populate-all that used to return `review_panel.html` returns a status chip. Reload still shows the list (001D). That is already accepted there.
- `batch: 0` restores one-request populate-all for tiny catalogs.

## Testing Strategy

- Unit: window of unfilled indices given *K*.
- Route TestClient: 25 stub rows, batch 10, assert 10 `run_populate` calls, progress `10/25`, load trigger present.
- Pause: second POST is pause; `run_populate` call count unchanged; HTML has Resume, no load trigger.
- Resume: skip 10 filled, compute next 10.
- `batch: 0` on 5 rows: one POST, no load trigger.
- No phrase text in the chip.
